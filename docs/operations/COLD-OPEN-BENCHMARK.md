# Cold-open benchmark (200 / 1000 changesets)

Status: harness only. This runbook does not change product behavior, schemas,
RPC contracts, native code, or deployment defaults. It records reproducible
cold-open evidence; Gate 0 target values remain open decisions.

## 1. Purpose

Measure what a fresh backend process pays to open a real iModel at an immutable
changeset target, at two history scales:

| Scale | Fixture | Intended use |
|---|---|---|
| 200 changesets | 200 real, sealed changesets | routine regression and arm comparison |
| 1000 changesets | 1000 real, sealed changesets | cold-open curve check; run only with an explicit time budget |

The harness has three parts:

1. `scripts/bench/prepare.mjs` creates or validates a benchmark fixture.
   `create` creates an isolated iTwin/iModel in a loopback stack, waits for the
   real baseline, then generates real changesets through
   `BriefcaseDb.pushChanges` (official HubAccess). It never writes fake
   changeset rows or fake `.changeset` files.
2. `scripts/bench/run.mjs` measures cold opens. Each sample is a fresh Node
   process; in cold mode it also gets a fresh local briefcase cache.
3. `scripts/bench/cold-open-runner.mjs` performs one sample (Hub resolve,
   optional native download/apply/open, ECSql probes) and writes one result
   file. It is spawned by `run.mjs` and is not normally invoked by hand.

Reports are written as `report.json` (schema `bench.cold-open.report.v1`) and
`report.md` next to each run.

## 2. What is measured

| Metric | Unit | Meaning |
|---|---|---|
| `hub.resolve.ms` | ms | GET iModel + complete changeset chain + target checkpoint + baseline metadata |
| `download.bytes` | bytes | Expected payload for the arm: checkpoint size (Hub metadata, native checkpoint file size when the Hub projection omits it) plus sealed changeset `fileSize` for the applied range |
| `download.changesetBytes` | bytes | Sum of changeset `fileSize` in the applied range |
| `download.checkpointBytes` | bytes | Baseline/checkpoint object size when available |
| `native.download.ms` | ms | `BriefcaseManager.downloadBriefcase` at the arm start point (baseline index 0 or the resolved checkpoint) |
| `native.openWritable.ms` | ms | Local `BriefcaseDb.open` used for the pull |
| `native.pullApply.ms` | ms | `BriefcaseDb.pullChanges({ toIndex })` applying the remaining changesets |
| `native.openReadonly.ms` | ms | Local read-only `BriefcaseDb.open` at the target |
| `native.firstTree.ms` | ms | First ECSql tree proxy query (`bis.DefinitionPartition`, falling back to `bis.Element`) |
| `native.firstBodies.ms` | ms | First ECSql body proxy query (`bis.GeometricElement3d`) |
| `native.firstSketch.ms` | ms | First ECSql sketch query; only when `LubanCAD.Sketch` exists in the fixture |
| `native.changesetsApplied` | count | Number of changesets applied by the pull |

Percentiles use R-7 linear interpolation (`p50`, `p95`; method recorded in the
report). `download.bytes` is derived from Hub metadata, not from an OS socket
counter.

### Arms

- `baseline`: download the baseline (checkpoint index 0), then pull every
  changeset up to the target.
- `checkpoint`: download the nearest successful checkpoint at or before the
  target, then pull the remaining changesets. This arm fails closed with
  `CHECKPOINT_ARM_UNAVAILABLE` when the Hub has no post-baseline successful
  checkpoint. The harness does not synthesize checkpoints and does not enable
  `CHECKPOINT_GENERATION_ENABLED` on its own.

### Cold versus warm

- `--mode cold` (default): fresh process and fresh local briefcase cache per
  sample. OS page cache, DNS cache and network caches are not flushed.
- `--mode warm`: fresh process per sample, but the first sample's downloaded
  briefcase file is reused by later samples. Sample 1 is marked `cold: true`;
  later samples are `cold: false` and report `native.download.ms = 0`.

## 3. Correctness gates

A run is only `PASS` when all of the following hold:

1. Hub head id/index equals the fixture manifest head before the run.
2. Hub target id/index equals the fixture manifest target before the run.
3. Every sample's native briefcase ends at exactly the target id/index.
4. Hub head id/index is unchanged after the last sample.
5. Every requested sample completed with `ok: true`.
6. No fatal blocker exists.

The report records `correctness.pass`, `targetUnchanged`, `headUnchanged`,
before/after head values, and an explicit failure list. A changed head is a
failure, not a warning: the benchmark must never write to the benchmark iModel.

## 4. Preconditions

- Node.js 24 (global `fetch`, `performance`, `node:test`).
- Repository root `.env` generated by `scripts/generate-env.ps1`. The harness
  reads `IMODELHUB_ADMIN_EMAIL` / `IMODELHUB_ADMIN_PASSWORD` /
  `IMODELHUB_API_KEY`; it never takes secrets on the command line and redacts
  them from reports. `BENCH_HUB_TOKEN` is an optional pre-issued JWT; when set,
  no email/password login is performed. `run.mjs` obtains one token during
  preflight and passes it to each sample process through the environment, so a
  multi-sample run does not multiply Hub login attempts (the default login
  bucket is 5 per 15 minutes).
- Native artifacts: either
  - `dist-backend/modeling-server` produced by `scripts/fetch-backend.ps1`, or
  - a private `modeling-server` checkout with `node_modules` (pass
    `--package-dir`). The directory must resolve `@itwin/core-backend`,
    `@itwin/imodels-access-backend`, `@itwin/imodels-client-authoring`,
    `@itwin/object-storage-azure` and `@bentley/imodeljs-native`.
- Docker Desktop with the stack images already available (public GHCR images).
  The isolated override uses Compose `!override` port lists (Compose v2.24+).
- An **isolated** stack. Never create/delete benchmark resources in a live
  environment. `prepare create` and `cleanup` require an explicit Hub URL,
  refuse non-loopback URLs, and refuse the checked-in live-stack ports
  (`5400`, `5401`, `5402`, `5301`). `run.mjs` also requires an explicit
  `--hub-url` or `BENCH_HUB_URL`; it never defaults to the live stack.

### Isolated stack

The override moves all published ports off the live stack and points the
webhook-agent at an unreachable modeling-server so it cannot forward events
into the live MS. Use a unique project name per run.

```powershell
$Project = "tkbench-$(Get-Date -Format yyyyMMddHHmmss)"
docker compose -p $Project `
  -f docker-compose.yml `
  -f scripts/bench/isolated-compose.override.yml `
  up -d postgres redis maildev azurite imodelhub webhook-agent
```

Ports in the isolated stack:

| Service | Isolated host port |
|---|---|
| imodelhub | 15400 |
| webhook-agent | 15402 |
| azurite blob/queue/table | 11500 / 11501 / 11502 |
| maildev | 11080 |

The baseline is generated asynchronously by the webhook-agent recovery checker
(1-minute interval in the override). `prepare create` waits for
`state=initialized`.

Harness environment for the isolated stack:

```powershell
$env:BENCH_HUB_URL        = "http://127.0.0.1:15400"
$env:AZURE_BLOB_ENDPOINT  = "http://azurite:10000/devstoreaccount1"
$env:AZURE_BLOB_PUBLIC_HOST = "127.0.0.1:11500"
$env:IMJS_AZURE_BLOB_BASE_URI = "http://127.0.0.1:11500/devstoreaccount1"
```

`AZURE_BLOB_ENDPOINT` is the Hub's signing endpoint (container-internal
`azurite:10000`). `AZURE_BLOB_PUBLIC_HOST` is the host-reachable equivalent;
the native driver rewrites only the matching host (SAS signatures do not cover
the hostname). `IMJS_AZURE_BLOB_BASE_URI` is the CloudSqlite container endpoint.

## 5. Commands

### 5.1 Unit tests

```powershell
node --test "scripts/bench/lib/*.test.mjs"
```

Covers R-7 percentile math, report schema/verdict/redaction, strict argument
validation, resource-name safety, and manifest chain/size/hash invariants.

### 5.2 Prepare a 200-changeset fixture

`create` has no Hub default: pass `--hub-url` (or export `BENCH_HUB_URL`) and
confirm with `--yes`.

```powershell
node scripts/bench/prepare.mjs create `
  --count 200 `
  --out .\bench-out\200 `
  --hub-url http://127.0.0.1:15400 `
  --max-minutes 25 `
  --wait-minutes 10 `
  --yes
```

Outputs:

- `bench-out/200/manifest.json` — fixture contract (200 chain entries,
  target/head, baseline/checkpoint availability, source ids, repository
  provenance).
- `bench-out/200/run-state.json` — resource ids used by `cleanup`.
- `bench-out/200/prepare-report.json` — timings, native versions, blockers.

Optional content verification (downloads and SHA-256-hashes every sealed
changeset; expensive for 1000):

```powershell
node scripts/bench/prepare.mjs create ... --verify-downloads
```

Validate an existing manifest without touching the Hub:

```powershell
node scripts/bench/prepare.mjs validate `
  --manifest .\bench-out\200\manifest.json `
  --count 200
```

Validate manifest plus on-disk fixture files (`--verify-files` requires a
manifest that actually references `file` paths; a Hub-generated manifest has
none and fails closed rather than claiming verification):

```powershell
node scripts/bench/prepare.mjs validate `
  --manifest .\bench-out\200\manifest.json `
  --count 200 `
  --verify-files `
  --bundle-dir .\bench-out\200
```

### 5.3 Run a 200-case baseline cold open

```powershell
node scripts/bench/run.mjs `
  --fixture .\bench-out\200\manifest.json `
  --out .\bench-out\run-200-baseline `
  --count 200 `
  --arm baseline `
  --mode cold `
  --samples 5 `
  --hub-url http://127.0.0.1:15400
```

Checkpoint arm (only if a post-baseline successful checkpoint exists):

```powershell
node scripts/bench/run.mjs `
  --fixture .\bench-out\200\manifest.json `
  --out .\bench-out\run-200-checkpoint `
  --count 200 `
  --arm checkpoint `
  --mode cold `
  --samples 5 `
  --hub-url http://127.0.0.1:15400
```

Expected fail-closed behavior: if the fixture says
`checkpoint.available=false`, or the Hub no longer exposes that checkpoint, the
run writes a `BLOCKED` report with `CHECKPOINT_ARM_UNAVAILABLE` and exits 2.
Do not edit the manifest to bypass this gate.

### 5.4 1000-case scale check

Only run after the 200 case is green and with an explicit budget. Preparation
pushes 1000 real changesets and can take a long time.

```powershell
node scripts/bench/prepare.mjs create `
  --count 1000 `
  --out .\bench-out\1000 `
  --hub-url http://127.0.0.1:15400 `
  --max-minutes 180 `
  --wait-minutes 10 `
  --yes

node scripts/bench/run.mjs `
  --fixture .\bench-out\1000\manifest.json `
  --out .\bench-out\run-1000-baseline `
  --count 1000 `
  --arm baseline `
  --mode cold `
  --samples 3 `
  --sample-timeout-ms 1800000 `
  --max-minutes 120 `
  --hub-url http://127.0.0.1:15400
```

### 5.5 Clean up

Delete only the resources recorded in the prepare state:

```powershell
node scripts/bench/prepare.mjs cleanup `
  --state .\bench-out\200\run-state.json `
  --yes
```

Then remove the isolated stack and its volumes:

```powershell
docker compose -p $Project `
  -f docker-compose.yml `
  -f scripts/bench/isolated-compose.override.yml `
  down -v
```

`cleanup` refuses state files that are not marked `benchmark: true` or whose
resource names are not `bench-*` / `bench-cold-open-*`.

## 6. Report contract

`report.json` schema `bench.cold-open.report.v1` contains:

- `environment`: Node/OS/CPU/memory, git commit, branch, tag, `describe`,
  dirty state, Hub URL, native package directory.
- `config`: count, requested/completed samples, percentile method, mode, arm.
- `fixture`: fixture id, changeset count, target/head, checkpoint, source.
- `native`: availability and package versions, or a blocker.
- `samples[]`: per-sample metrics, checks, details, errors.
- `metrics`: count/p50/p95/min/max/mean for each measured metric.
- `correctness`: pass, target/head unchanged flags, before/after head,
  failures.
- `blockers[]`: fail-closed reasons with stable codes.
- `limitations[]`: what the evidence does not cover.

`report.md` renders the same data for review. Reports never contain
passwords, bearer tokens, API keys or SAS signatures.

## 7. Blocker codes

| Code | Meaning |
|---|---|
| `NATIVE_RUNTIME_UNAVAILABLE` | Native packages/addon are not resolvable from `--package-dir` |
| `NATIVE_HOST_START_FAILED` | `IModelHost.startup` failed |
| `AUTH_CREDENTIALS_MISSING` | Hub admin email/password are absent |
| `HUB_AUTH_FAILED` / `HUB_HTTP_ERROR` / `HUB_UNREACHABLE` | Hub login or REST call failed |
| `BASELINE_TIMEOUT` / `BASELINE_FAILED` | webhook-agent baseline did not reach `initialized` |
| `NATIVE_PREPARE_FAILED` | Real changeset generation failed |
| `PREPARE_TIME_BUDGET_EXCEEDED` | Generation stopped at `--max-minutes` |
| `CHECKPOINT_ARM_UNAVAILABLE` | No successful post-baseline checkpoint for the checkpoint arm |
| `BASELINE_CHECKPOINT_MISSING` | Hub has no successful baseline checkpoint at index 0 |
| `NATIVE_TARGET_MISMATCH` | Native briefcase did not end at the target changeset |
| `FIXTURE_TARGET_MISMATCH` | Hub chain no longer matches the fixture manifest |
| `RUN_TIME_BUDGET_EXCEEDED` | Runner stopped at `--max-minutes` |
| `SAMPLE_TIMEOUT` / `SAMPLE_NO_RESULT` | Sample process exceeded its timeout or produced no result |
| `REPORT_INVALID` | Report did not satisfy the schema; no report is published |

## 8. What this proves and does not prove

Proves, when the verdict is `PASS`:

- The fixture contains the requested number of real, sealed changesets with a
  contiguous parent chain and stable head/target ids.
- A fresh process (and fresh local cache in cold mode) can resolve the Hub
  state, download the selected arm, apply the remaining changesets, open the
  briefcase read-only, and execute the read probes.
- Target id/index and head id/index did not change during measurement.
- p50/p95 values for each measured phase are reproducible from the JSON
  report and the recorded commit/tag.

Does not prove:

- Full UI or modeling-server FeatureOp latency. `firstTree`/`firstBodies`
  are ECSql storage probes, not the rendered tree, viewport, or feature-eval
  pipeline.
- Cold operating-system caches. Only the process and local briefcase cache are
  guaranteed fresh.
- Exact network bytes. `download.bytes` is Hub-metadata-derived; checkpoint
  container internals may transfer a different number of bytes.
- Sketch performance when the fixture has no `LubanCAD.Sketch` schema. The
  phase is reported unsupported rather than fabricated.
- Checkpoint generation behavior. The checkpoint arm requires an externally
  produced successful checkpoint; the harness does not enable or run the
  checkpoint worker.
- Any Gate 0 acceptance threshold. This runbook records measurements only.

## 10. Known constraints

- The 200/1000 fixture is intentionally not committed: it contains real
  changeset bytes and storage metadata. Regenerate it in an isolated stack and
  keep artifacts outside git.
- `prepare create` creates a new iTwin/iModel per run. If it fails after
  resource creation, the state file is retained for `cleanup`; no automatic
  deletion is attempted.
- The native driver always downloads an explicit version: `IModelVersion.first()`
  for a baseline-only chain, or the observed head changeset id when resuming.
  Implicit "latest" on an empty chain was observed to stall after the
  checkpoint bytes arrived in the local stack (2026-11-24).
- The harness uses Hub metadata for changeset sizes. A Hub that does not expose
  the checkpoint size yields a report with `download.changesetBytes` and no
  `download.bytes` (lower-bound evidence), never an invented number.
- The isolated compose override is for benchmark evidence only. It raises
  throttler limits and must not be used as a production deployment profile.
- `BENCH_HUB_TOKEN` / the propagated preflight token is used until it expires;
  the harness does not refresh it. A run longer than the token lifetime fails
  closed with a Hub 401 rather than silently starting a new login storm.

## 11. Isolated run evidence (2026-11-24)

This is the first end-to-end run of the harness. It is evidence that the
harness works and that the report gates are effective; it is **not** a hardware
or release baseline. The isolated stack and all volumes were removed after the
run, and the fixture iTwin/iModel were deleted through `prepare cleanup`.

### Fixture

| Item | Value |
|---|---|
| Scale | 200 real sealed changesets (no fabricated changeset rows) |
| Generation | 58.7 s (`BriefcaseDb.pushChanges` per changeset) |
| Baseline initialization | 20.1 s (webhook-agent recovery checker) |
| Baseline payload | 4,194,304-byte checkpoint file |
| Changeset payload | 63,039 bytes across 200 sealed changesets |
| Target = head | index 200, id `9a5eae50c7022733da9a7745c49723ef40cbfdde` |
| Checkpoint arm | `available: false` (no post-baseline successful checkpoint) |

### Baseline arm, 3 cold samples

| Metric | p50 | p95 |
|---|---:|---:|
| `hub.resolve.ms` | 4,419.9 | 4,640.8 |
| `download.bytes` | 4,257,343 | 4,257,343 |
| `native.download.ms` | 56,498.1 | 63,594.4 |
| `native.pullApply.ms` | 7,347.1 | 9,011.4 |
| `native.openReadonly.ms` | 39.1 | 41.0 |
| `native.firstTree.ms` | 2.4 | 2.5 |
| `native.firstBodies.ms` | 2.0 | 2.1 |
| `native.firstSketch.ms` | n/a | n/a (probe unsupported: no `LubanCAD.Sketch`; no fake latency emitted) |

Verdict: `PASS`, 3/3 samples, target id/index unchanged, head id/index
unchanged before and after. `download.bytes` came from the native checkpoint
file size because the Hub projection did not expose the V2 container size.

Environment: Node v24.20.0, win32/x64, 16 vCPU, 31.5 GiB RAM, repo commit
`b080f0e6fab637a50ad447e35576f433df93597c`, tag `backend-20261110`, describe
`backend-20261110-391-gb080f0e6fa-dirty`.

### Checkpoint arm

Verdict: `BLOCKED` (`CHECKPOINT_ARM_UNAVAILABLE`, exit 2). The final fixture had
no successful checkpoint after baseline index 0, so no checkpoint-arm sample
was attempted. This is the intended fail-closed behavior; the harness did not
fabricate a checkpoint.

### Interpretation caveats

- `native.download.ms` was 47-64 s for the 4 MiB checkpoint in this local
  Docker Desktop/Azurite environment, while applying 200 changesets took
  7-9 s. The download path is the dominant cost here and deserves a separate
  investigation (host rewriting, Azure SDK retry behavior, Docker networking)
  before any Gate 0 target is set.
- The 1000-case fixture was not generated in this run. It remains a planned
  scale check with an explicit time budget.
- Warm mode (`--mode warm`, reuse of the first sample's briefcase) is
  implemented but was not exercised in this evidence run.
- The measured values must not be compared across machines without recording
  the environment block and the isolated-stack port mapping.
