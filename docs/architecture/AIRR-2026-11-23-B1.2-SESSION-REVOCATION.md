## 1. 目标与验收

### 1.1 问题（只读审计证据）

- `src/auth/strategies/jwt.strategy.ts` 只查用户存在与 `status=active`；**不查 sessionId 对应会话是否存在**。
- `POST /auth/logout` 删除（软删）session 行，但旧 access token 继续通过 `/auth/me` 与所有 `AuthGuard('jwt')` 路由。
- access token 载荷已有 `sessionId`，但没有任何校验使用它；无 `jti`/denylist。
- `POST /auth/refresh` 有原子 hash 轮换（L-02），但轮换前签发的 access token 仍可用。
- `reset/password` 删除该用户全部 session；`PATCH /auth/me` 改密删除**除当前会话外**的 session；两种情况下旧 access token 仍可用。
- 账号 `inactive`/软删已由现有 status/user 检查拒绝（B1.1），本切片不得回退该行为。

### 1.2 可观察验收标准

1. 登录签发的 access token 绑定 `sessionId` + `sessionHash`（session 行当前 hash）；JWT 策略每次受保护请求校验：
   - 会话行存在（软删/登出即不存在）；
   - 会话属于 token 的 `sub/id`；
   - `session.hash === payload.sessionHash`；
   - 再执行现有用户存在 + `status=active` 检查。
2. `login → logout → 旧 access token` 下一个请求 401。
3. `refresh` 成功轮换后，轮换前 access token 下一个请求 401；新 access token 可用；旧 refresh token 复用仍 401。
4. `reset/password`（删除全部会话）后旧 access token 401。
5. `PATCH /auth/me` 改密（删除其他会话、保留当前会话）后：**其他会话**旧 access token 401；当前会话按既有产品语义保留，其 token 仍可用（除非另开切片改为全登出）。
6. 管理员停用/软删账号后旧 access token 401（保留现有 B1.1 行为）。
7. 缺少 `sessionId`/`sessionHash` 的旧 token（部署前签发）立即 401，**无静默 legacy 路径、无兼容开关**；用户重新登录即可。
8. 活跃 token、cookie/header 传输、MS `/auth/me` 校验调用方式不变。

### 1.3 非目标

- 不做 MS WebSocket 连接建立后的周期复验/关闭（B1.2b）。
- 不做 BFF/MS 的 60s token 验证正缓存失效（跨仓后续切片；本切片只保证 Hub 下一请求 401）。
- 不引入 `jti` denylist、Redis 撤销表、session TTL/expiresAt。
- 不改 OIDC 授权码/设备码/RS256 token 流程；OIDC 浏览器会话 cookie 仍只由 `/oauth` 解析（其 token 无 session 绑定，将被通用 JWT 策略拒绝，属预期的权限收敛）。
- 不改账号生命周期、登录/刷新/密码规则、限流。
- 不做 schema 迁移。
- 不勾选 G1 Gate。

## 3. 复用决策矩阵

| 需求能力 | 候选复用 | 覆盖度 | 决策 | 理由 | 许可证 |
|---|---|---|---|---|---|
| token 会话绑定 | 现有 `session.hash`（refresh 轮换 CAS 已维护） | 高 | **复用**，作为 access token 的 `sessionHash` claim | 无需新列/迁移；轮换天然失效旧 access token；不引入第二撤销存储 | MIT（仓内） |
| 会话查找 | `SessionService.findById`（软删过滤 + user eager） | 高 | **复用** | 与 refresh/logout 同一事实源 | MIT（仓内） |
| 账号状态 | 现有 `UsersService.findById` + `StatusEnum.active` | 高 | **保留**（不合并、不缓存） | 遵守“保留账号状态检查”；语义不变 | MIT（仓内） |
| 撤销机制 | jti denylist / session version / hash 绑定 | 中 | 选 **hash 绑定** | 最小、无 schema；denylist 需要新存储与清理，session version 需要迁移 | — |
| 缓存 | 短正缓存 | — | **不采用** | 会延迟“下一请求 401”；负缓存也不采用（避免掩盖恢复/误导） | — |

**规则**：没有新增认证路径；所有改动集中在既有 token 签发与既有 JwtStrategy。

## 5. 数据/事务/安全

- 数据事实源：`session` 表（id/user/hash/deletedAt）仍是会话事实源；不新增表/列。
- 事务：JWT 校验是只读；不进入写事务。logout/refresh/改密仍沿用现有写路径。
- Undo/HITL：不适用。
- 写租约/限流：不改变。
- 密钥/日志/审计：
  - `sessionHash` 来自 session 行；access token 中携带该 hash 仅用于绑定校验，不是 refresh token 本身，也不得写入日志。
  - 401 不返回 token/claims/session 细节；不新增日志中的 token。
  - 审计事件（B7）不在本切片；拒绝路径保持静默 401。

### 5.1 失败语义

| 场景 | 结果 |
|---|---|
| 无 sessionId 或 sessionHash（旧 token） | 401，不查用户/会话（fail closed） |
| session 行不存在（logout/软删/重置） | 401 |
| session.hash 不匹配（合法 refresh 轮换后旧 token） | 401 |
| session 属于其他用户（伪造/串用 sessionId） | 401 |
| 用户 inactive/软删/不存在 | 401（现有 B1.1 语义） |
| DB 暂时不可用 | 请求失败关闭（异常 → 401/500 由 Nest 处理；不得放行） |
| OIDC 浏览器 session cookie 当 Bearer 使用 | 401（无 sessionId/sessionHash） |

### 5.2 非用户 token 路径审计（fail-closed）

| 路径 | 形态 | B1.2a 后行为 |
|---|---|---|
| Hub access token | `AuthService.getTokensData`，带 `sessionId`+`sessionHash` | 通过会话校验；唯一普通用户 access token 路径 |
| MS 服务账号 | 走 `/auth/email/login` 正常登录（`ServiceAccountAuthClient`） | 同样获得 session 绑定；不破坏服务调用 |
| OIDC 浏览器 cookie | `issueBrowserSession`：同 `auth.secret`，`typ=oauth-browser`、独立 aud，无 sessionId | 通用 JWT 策略因缺 `sessionId`/`sessionHash` 拒绝；`/oauth` 自有 `resolveBrowserSession` 校验，不受影响 |
| OIDC ID token | JWT（RS256 或 fallback），`sub/aud/iss/scope`，无 sessionId | 作为 Bearer 调 `/auth/*` 时 fail closed；OIDC 端不用通用 `AuthGuard('jwt')` |
| OIDC access/refresh token | Redis 中的不透明随机串，不是 JWT | 通用 JWT 策略无法接受；OIDC 自有 introspection |
| refresh token | `auth.refreshSecret` 签名 | 只能走 `jwt-refresh` 策略；不能当 access token |
| forgot/confirm email token | `auth.forgotSecret`/`auth.confirmEmailSecret` 签名 | 与 access token 不同密钥，passport 验签失败 |
| API key / service channel | `X-API-Key`，非 JWT | 不走 JWT 策略；不因 B1.2a 改变 |

- 结论：没有“无 session 但仍可作为用户 access token”的静默路径；OIDC 浏览器/ID token 若被误用为 Bearer 会 401（新增单测 + 隔离 relational Hub e2e 的 OIDC 浏览器 JWT → 401 覆盖）。
- 未为任何非用户 token 开兼容口；不需要 `EXCEPTIONS.md` 新条目。

### 5.3 性能权衡（测量说明）

- 每个受保护请求：session 主键查询（1 次）+ 用户主键查询（1 次）。若先查 session 且会话无效，则跳过用户查询。
- 不采用正缓存：logout/轮换要求“下一请求”生效，缓存会引入 TTL 窗口；负缓存也不采用。
- 现网 QPS/延迟基线未在本切片测量；以上为查询次数层面的静态说明。后续若成为热点，可评估把用户状态并入 session 查询或引入带撤销广播的缓存（需新 ADR）。
