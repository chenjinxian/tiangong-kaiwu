## 1. 目标、可观察验收与非目标

### 1.1 目标

1. 给 modeling-server 增加显式写强制开关 `AUTH_B3_WRITE_MODE=off|enforce`（默认 `off`）。
2. 复用 B3.1c 的 OBO shadow 传输与 Hub 单一 resolver，不建第二套策略引擎。
3. 在 §3 列出的写入口先同步取得 Hub 对**精确动作集合**的决策；全部 allow 才继续现有 owner session、write lease 与 legacy 操作。
4. Hub 决策必须发生在任何 mutation、`getFeatureService`/`ensureInitialized`/`ensureWarm`、EditTxn、briefcase save/push/pull/abandon、lease acquisition 之前。
5. 默认 `off` 时零新 Hub 调用、legacy 行为逐字不变；回滚=改回 `off` 并重启，无数据/schema 迁移。

### 1.2 可观察验收

- `off`（默认）：现有写路径、session/lease/owner 行为与测试逐字不变；`pepCoverage` 只更新分类，不产生 Hub 调用。
- `enforce`：所有 §3 写入口在 deny 时返回 `AuthorizationDenied` 403；决策/凭据不可用时返回 `AuthorizationUnavailable` 503；绝不回退共享 key/JWT/服务账号或继续 legacy 写。
- gate 拒绝时**没有** lease 获取、服务初始化、ensureWarm、EditTxn、briefcase 预留、save/push/pull/abandon、直改方法调用或本地文件改动。
- `previewFeatureOp` 明确按写类处理（要求 `doc.write`）：它要求写租约，且 `ensureInitialized`/`ensureWarm` 可能执行冷重建 EditTxn 与 init 自动 push。
- 直改 `basicManipulationIpc`/`solidModelingIpc` 写方法在方法执行前经 `setDirectEditAclHook` 判定；deny 不执行方法，audit 记录稳定错误码。
- 写决策缓存 TTL 永不超过 **5s**（即使 Hub 返回更大值）；读决策仍 ≤30s。
- 错误消息与日志只含稳定 code/reason、entry、iModelId、actions、decisionId；不含 token/handle/OBO/决策请求体/客户端 secret。
- 隔离 Hub+MS canary 的写矩阵（§7.2）可重复通过；native 写/几何/真实 push 未跑时如实标注 unproven。

### 1.3 非目标（本切片明确不做）

- 不强制 `exportIModel`（B3.1f）；不做 Hub 路由级 guard/controller（B3.1e）、storage/tile、WA baseline、BFF、progress/retry。
- 不做 B4 Write 等级激活：本切片只消费当前 Hub action 目录（写=Manage 兼容，`authz-action.ts` 的 `P0_WRITE_SEMANTICS`）。不改 Hub。
- 不改变 push 的服务账号/归因（B6/X-21）；不做 B10 tenant、B7 WORM、B6 共享 key 退役。
- 不覆盖 undo/redo/reverseTxns、`toggleGraphicalEditingScope`、saved views/camera paths、assembly helpers、`closeIModel`；保持 `p0-not-covered`，B3 关闭前必须另行分类。
- 不做 editor 包命令启动点/命令内部 `endEdits` 保存点的二次授权（决定与残余见 §3.3）；不改 shared IPC/RPC 契约、不改前端。
- 不实现 handle 续期/WS ticket；handle 15m 到期后的 503 仍按 B3.1c 的 P2 前置处理。

## 2. 开关、前置、启动校验与回滚

| 变量 | 默认 | 允许值 | 本切片要求 |
|---|---|---|---|
| `AUTH_B3_WRITE_MODE` | `off` | `off`/`enforce` | 唯一写强制开关；`off` 是回滚 |
| `AUTH_OBO_MODE` | `off` | `off`/`shadow` | `enforce` 时**必须** `shadow` |
| `AUTH_OBO_SERVICE_NAME` | 无 | Hub allowlist 内名称 | `enforce` 时**必须**非空且与 Hub 一致 |
| `DIRECT_EDIT_GUARD_MODE` | `enforce` | `off`/`shadow`/`enforce` | `enforce` 时**必须** `enforce`；否则直改 ACL 钩子不会被 fail-closed 调用 |
| `AUTH_B3_READ_MODE` | `off` | `off`/`enforce` | **建议**先 `enforce`，但不硬性要求（理由见下） |
| `HTTP_STATEFUL_RPC_MODE` | `deny` | `deny`/`allow` | 建议保持 `deny`；`allow` 启动告警 |
| `SESSION_ISOLATION_MODE` | `enforce` | `off`/`shadow`/`enforce` | 建议保持 `enforce`；`off`/`shadow` 启动告警 |

**为什么写强制不硬依赖读强制**：写决策由 Hub 独立计算（当前 resolver 下 `doc.write` allow 通常蕴含至少 Read，不会出现写通过而读必然拒绝的倒挂）；把两者硬耦合会让读强制的回滚同时撤掉更高风险的写控制。但 write-only 部署仍允许只读用户经 download/open 取得 rw briefcase（读未强制），造成数据暴露与 UI 误导，因此发布序列应先启用 `AUTH_B3_READ_MODE=enforce`，启动日志在 read=off 时显式警告。若 owner 要求强一致，可在 `config.ts superRefine` 增加一条硬校验。

Hub 侧同批需按 B3.1c/B6 保持 `AUTH_OBO_ENABLED=shadow`、service identity（`X-Service-Token` 或显式 legacy key 回滚）与 `POST /internal/v1/authz/decisions` 可达；本切片不改 Hub。决策 `cacheTtlMs` 由 Hub 返回（当前非 `doc.read` 为 5s），MS 只做保守 clamp。

启动校验（`src/config.ts` `superRefine`）：

- `AUTH_B3_WRITE_MODE=enforce` 且 `AUTH_OBO_MODE!=shadow` → 启动失败并点名 `AUTH_B3_WRITE_MODE`。
- `enforce` 且缺 `AUTH_OBO_SERVICE_NAME` → 启动失败并点名 `AUTH_OBO_SERVICE_NAME`。
- `enforce` 且 `DIRECT_EDIT_GUARD_MODE!=enforce` → 启动失败并点名 `DIRECT_EDIT_GUARD_MODE`（直改 ACL 只能在 guard 的 enforce 分支 fail closed）。
- `enforce` 且 `AUTH_B3_READ_MODE=off`/`HTTP_STATEFUL_RPC_MODE=allow`/`SESSION_ISOLATION_MODE!=enforce` → 启动**警告**，不静默降级。
- 启动日志明确输出 `AUTH_B3_WRITE_MODE=enforce`、覆盖入口、read 模式、`AUTH_OBO_SERVICE_NAME`（不打印 secret）、回滚方式；`off` 也输出未强制状态。

**回滚**：`AUTH_B3_WRITE_MODE=off` 并重启。无数据/schema 迁移；进程重启清空内存 lease/handle/OBO/decision 缓存；Hub 已写 audit 保留。配置只在启动读取，不支持运行时翻转。

**实施 PR 的 `.env.example` 设计注记**（本设计不写该文件）：注释说明 `AUTH_B3_WRITE_MODE` 默认 `off`、enforce 前置（OBO shadow + service name + direct-edit guard enforce）、各入口动作映射与 403/503 fail-closed 语义，不写 secret。

## 3. 动作映射、顺序与直改

### 3.1 动作映射原则

- Hub 是唯一 PDP；MS 只做固定 action 映射，不本地解释 ACL、不覆盖 Hub deny。
- `doc.write`：编辑/提交能力（FeatureOp、PartStudio 元数据写、直改、lease、save、pull）。
- `changeset.push`：创建/上传 changeset 的 Hub 能力；push 同时要求 `doc.write`。
- `briefcase.write`：只改本会话 briefcase、不创建 changeset 的能力（abandon 丢弃本地改动）。pull 要读取上游 changeset（当前经 MS 服务账号，B6/X-21），故用更严的 `doc.write` 而不是 `briefcase.write`。
- 每个入口使用**精确动作集合**；OBO exchange 与 decision 使用同一集合，避免“只读 token 复用为写决策”。

### 3.2 入口/动作/顺序矩阵

| 入口 | 绑定 | enforce 动作 | gate 位置（先于任何副作用） |
|---|---|---|---|
| FeatureOp 写 | `LubanFeatureRpcImpl.applyFeatureOp` | `doc.write` | `guardKey(write=true)` 后，legacy scope 查询/`getFeatureServiceByKey`/`ensureInitialized`/`applyOp` 前 |
| FeatureOp 预览 | `LubanFeatureRpcImpl.previewFeatureOp` | `doc.write` | `guardKey` 后，`getFeatureServiceByKey`/`ensureInitialized` 前（写类决定见 §1.2） |
| 特征/零件改名 | `renameFeature` / `renameBody` | `doc.write` | `guardKey(write=true)` 后，`getFeatureServiceByKey`/`ensureInitialized` 前 |
| PartStudio 元数据写 | `createPartStudio` / `renamePartStudio` / `deletePartStudio` | `doc.write` | `guardKey(write=true)` 后，`registryFor(...)`/create/rename/remove 前 |
| 写租约 | `acquireWriteLease` | `doc.write` | `guardKey(write=true)` 后，`writeLeases.acquire` 前；每次调用（含 10s renew）都判定 |
| 本地提交 | `AppFunctionIpcHandler.saveChanges` | `doc.write` | `_assertKey(write=true)` → 解析文档身份 → gate → `_assertWriteLease` → 监听器/`db.saveChanges` 前 |
| 拉取 | `AppFunctionIpcHandler.pullChanges` | `doc.write` | `_assertKey(write=true)` → gate → `BriefcaseDb.findByKey`/progress/`pullChanges` 前 |
| 推送 | `AppFunctionIpcHandler.pushChanges` | `doc.write` + `changeset.push` | `_assertKey(write=true)` → gate → `_assertWriteLease` → progress/`BriefcaseDb.pushChanges` 前 |
| 放弃本地改动 | `AppFunctionIpcHandler.abandonChanges` | `briefcase.write` | `_assertKey(write=true)` → gate → `db.abandonChanges` 前 |
| 直接编辑 | `DirectEditWriteGate` 的 `setDirectEditAclHook` | `doc.write` | session/owner/read-only 检查后、lease 断言与方法调用前；每个写类方法 |
| 释放租约 | `releaseWriteLease` | 不强制 | 保持现有 owner 检查；释放是安全操作 |

**顺序不变量**

1. 先保留现有 `guardKey`/`_assertKey`/`assertSessionKeyAccess`/version-read-only 检查，再解析文档身份；身份只取已打开 db 的 `iModelId/iTwinId` 或本 session 的 `BriefcaseRecord`，绝不信任客户端 `sessionId`/`user`/路径。
2. 文档身份缺失、无 session → `AuthorizationDenied` 403（生产 `/ipc` 必有 session；单元/CLI 在 `off` 下不受影响）。
3. Hub 决策在 mutation/服务初始化/EditTxn/lease acquisition 之前；save/push/pull/abandon 的进展回调、状态 map、registry 计数也都在 gate 之后。
4. save/push 的 `_assertWriteLease` 是纯断言、无副作用；放在 gate 之后，使 ACL deny 先于 `DocumentLocked`，同时保留租约检查存在性。直改沿用现有顺序：owner/read-only → ACL → lease。
5. deny/unavailable 路径不得继续执行 legacy 分支；不得先写后判、不得以 no-op 成功掩盖拒绝。

**行为变化提示**：legacy `saveChanges`/`abandonChanges` 在 db 不存在时是 no-op；enforce 下无法解析文档身份时改为 403（fail closed），canary 需确认前端不依赖该 no-op。`acquireWriteLease` 的文档身份依赖已打开 db；前端当前只在可写 connection 上取租约（`useEditorSession`），未跑真栈前按 unproven 处理。**内部 push 旁路说明**：`FeatureService.maybePush`/`PartStudioRegistry.pushQuietly`/`briefcasePush` 会在已授权的 apply/init/rename 内调用 `db.pushChanges`，不经过 `AppFunctionIpcHandler.pushChanges`。这是已授权写操作的一部分（当前 `doc.write` 已含 changesets Manage），不是独立入口；不额外要求 `changeset.push`，也不放宽 gate。

### 3.3 直改（`DirectEditWriteGate` + `setDirectEditAclHook`）

- 仅在 `AUTH_B3_WRITE_MODE=enforce` 时安装 hook；`off` 不安装，行为与 G1 C3.3 相同。安装顺序改为先 `setDirectEditAclHook(...)` 再 `installDirectEditWriteGate()`，使启动日志的 `(ACL hook)` 准确。
- hook 输入已由 `assertDirectEditWrite` 从服务器侧派生：`actor.userId/sessionId` 来自 `SessionContext.require()`，`document.docId/iTwinId/briefcaseId` 来自 `BriefcaseRecord`/db。hook 只使用这些字段；优先用 `SessionContext.current()` 且校验 `sessionId` 一致，否则 `sessionRegistry.get(actor.sessionId)`。
- 若 `BriefcaseRecord.iTwinId` 缺失，gate 在调用 hook 前从已打开 db 回填 `iTwinId`；仍缺失 → deny。该回填是对 `DirectEditWriteGate.ts` 私有的补充，不改变现有公共契约。
- hook 调用 `WriteAccessGate.require({entry:'direct-edit', iTwinId, iModelId: docId, actions:['doc.write']}, session)`；**抛出** `AuthorizationDenied`/`AuthorizationUnavailable`，不返回 `false`（`false` 会被 `DirectEditWriteGate` 映射为 `SessionOwnership`，丢失 403/503 语义）。`DirectEditWriteGate` 现有 catch 会先 audit 再 rethrow，满足审计要求。
- 命令**启动点不做 ACL**：`EditorAppHandler.startCommand` 只做 owner/key 检查，构造 `EditCommand` 不启动 EditTxn、不写库。命令运行中在角色撤销/deny 后，下一次写类方法在 hook 处被拒；已完成的写方法在 `endEdits`/`saveChanges`（editor 包 `NON_WRITING_METHODS`）提交，属“写入时已授权”的既成事实，缓存窗口内可能提交。这是本切片的明确边界：若 owner 要求在保存点硬拒，需在 editor 包把 `endEdits`/`saveChanges` 分类为写并重建 viewer `dist`，另立切片（不在本切片）。
- `basicManipulationIpc`、`solidModelingIpc` 都经 `EditorAppHandler.callMethod`；未知方法按写类 fail closed。`abandonChanges`/`abandonEdits` 保持非写类，避免撤销角色后无法丢弃本地改动。

## 4. 判定语义、Deny 优先级与错误面

```text
AUTH_B3_WRITE_MODE=off → legacy（零 gate 调用）
enforce:
  1. 无 session / 文档身份缺失 → AuthorizationDenied（403）
  2. 等待在途 handle provisioning（≤ Hub 超时 +1s）；失败 → AuthorizationUnavailable（503）
  3. 无 handle / handle 过期/用尽 / session 撤销 → AuthorizationUnavailable（503）
  4. OBO exchange 或 Hub decision 超时/5xx/网络/非法响应 → AuthorizationUnavailable（503）
  5. Hub 明确策略 deny（含 share deny、insufficient_permission/scope、imodel/cross-itwin、service account） → AuthorizationDenied（403）
  6. 全部动作 allow → 继续现有 owner/lease/legacy 写路径
```

- 只允许“决策允许**全部**请求动作”才放行；aggregate allow 但 action map 有 deny 也按 deny 处理。
- Deny 优先级完全来自 Hub（账号/session 硬门禁 → 显式 deny/share denyList/link → grant → 默认拒绝）；MS 不覆盖、不缓存“本地 allow”来对抗 Hub deny； deny 决策缓存最长 5s。
- 不重试共享 key/JWT/服务账号，不因 deny 继续 legacy，不把 deny 写成 no-op 成功。
- 错误沿用 `SessionError`：`AuthorizationDenied` 403、`AuthorizationUnavailable` 503；消息只含稳定 reason/code，不含 token/handle/OBO/请求体。
- 本地副作用：FeatureOp 在 `getFeatureService`/`ensureInitialized` 前拒绝；save/push/pull/abandon 在 db 调用/进展回调前拒绝；lease 在 `writeLeases.acquire` 前拒绝；直改在方法调用前拒绝。deny 不自动 release 已持有的 lease（见 §5.3）。
- UI：403 视为需权限/换账号的终态；503 可重连/重试（重新签发 handle），不得静默降级为只读可用写。前端 `usePermissions` 对非 403 错误回退 editable 的既有问题不属于本切片，但服务端始终拒绝，不构成旁路。
- Hub decision 端点仍返回 `mode=shadow`；MS 的 `AUTH_B3_WRITE_MODE=enforce` 只是本地 PEP 拒绝，不等于 Hub 路由/数据面已强制（B3.1e），也不改变 Hub audit 的 shadow 标记。

## 5. OBO 正确性、缓存与租约

### 5.1 scope-keyed OBO 与决策缓存

- OBO cache key 沿用 B3.1c：`${iModelId}|${actions.sort().join(',')}`；命中还须 `grantedScopes` 覆盖全部动作。写集合（`doc.write`、`doc.write+changeset.push`、`briefcase.write`）不会复用 `doc.read` token；反之亦然。
- 决策 key 同理按 iModel+精确动作集合；新 OBO 产生时清除该 iModel 的旧 decisions（B3.1c 已有）。
- 实现需把 `OboShadowSettings.enforceRead` 扩展为 `enforceRead | enforceWrite`；`authorize` 在任一 enforce 开启时可用，但每个 gate 仍只在自己的 mode 下调用。`OboShadowEntry` 需拆出读/写子集，避免 `ReadAccessGate` 误接受写 entry。
- 写集合的决策 TTL 在 MS 侧强制 clamp 到 **5s**：`ttl = min(Hub.cacheTtlMs, actions 全为 doc.read ? 30s : 5s)`；即使 Hub 返回 30s 也绝不缓存 30s。负决策同样 ≤5s；不可用结果不缓存。
- 失败不缓存为 allow；session 关闭清空 handle/OBO/decisions（既有 `onSessionClose`）。

### 5.2 handle 预算与 provisioning

- 写入口与读入口共用同一个 WS 升级 handle（15m、默认 max uses 16）。每个新 scope 集合 exchange 消耗一次 use；OBO TTL 5m、剩余 <2m 重新 exchange。一个活跃编辑器可能同时使用 `doc.read`、`doc.write`、`doc.write+changeset.push`、`briefcase.write` 四套，15m 内 exchange 次数可能接近/超过 16（尤其同时 read+write+push+pull）。
- 决策调用不消耗 handle uses，但 lease 每 10s renew + save 频繁触发会产生 Hub decision 流量（5s 缓存下最坏约 1 次/5s/用户）；canary 必须记录 exchange/decision 次数与 p95。
- 若 handle 用尽 → `handle_exhausted` → 503，直到重连换新 handle。**这是写强制上线的阻塞项之一**：需在 canary 决策是否提高 Hub `AUTH_OBO_HANDLE_MAX_USES` 或实现 handle 续期；不得在 MS 侧绕过。
- 首个写可能先于 WS 升级的 fire-and-forget provisioning 到达；`authorize` 已有有界等待（Hub 超时 +1s），写 gate 复用该等待；超时 → 503。

### 5.3 与 write lease 的交互

- `acquireWriteLease`：gate 通过后才 `writeLeases.acquire`；deny/unavailable 不创建租约。renew 也走同一 gate，因此撤销后最迟 30s 租约自然过期，其他 session 可接管。
- 已持有租约后某次写被 deny/unavailable：**不自动释放租约**。理由：租约是编辑槽位而非授权凭证；自动释放会破坏本地未保存编辑状态并可能被其他 session 抢占。授权仍由每次写决策 5s 内复查；租约 30s TTL 与 session close 清理兜底。
- `releaseWriteLease` 不做 ACL（释放无数据面影响）；session close 仍按现有流程释放 lease/registry。
