## 1. 目标与审计事实

### 1.1 审计事实

- MS 的 `/ipc` 与 `/ws` 只在升级时校验一次 Hub token；连接建立后不再复查（`src/middleware/wsAuth.ts`、`src/main.ts`）。
- token 校验有 60s 正缓存；无效结果也会缓存 60s（B1.2a 时；B1.2c 已改为默认 0 且负结果永不缓存）。
- Hub logout 删除 session 后，已建立的 MS WebSocket 仍保持，直到客户端关闭/进程重启。
- B1.2a 已让 Hub 在每个请求上校验 session；但 MS 的 WS 不在请求路径上，仍需要周期复查。

### 1.2 关键设计约束：refresh 轮换不能误断编辑器

B1.2a 让 refresh 轮换改变 session hash，从而撤销轮换前的 access token。若 MS 周期复验直接拿 WS 升级时的旧 token 调 `/auth/me`：
- 每次合法 token refresh（前端约每 10 分钟）后，复验都会 401；
- MS 若把 401 当撤销，就会在每次 refresh 后关闭正在编辑的 WS，形成稳定回归。

因此本切片**不复验“旧 token”**，而是复验“Hub 会话是否仍存活”：
- Hub 新增 `GET /internal/auth/sessions/:sessionId/status?userId=<id>`，仅服务间调用；
- 返回 `{ active: boolean }`，与 token hash 轮换无关；
- MS 从已验 token 中只取 `sessionId`/`userId`，不保留 token 用于复验。

### 1.3 验收标准

1. WS 升级成功后，verified principal 的 Hub `sessionId` 被保存到本地会话记录（`hubSessionId`）。
2. 每个带 `hubSessionId` 的 `/ipc`/`/ws` socket 按 `WS_AUTH_REVALIDATE_INTERVAL_MS`（默认 30s，最小 1000ms）周期调用 Hub session-status。
3. `active=true`：保持连接并记录 `lastAuthValidatedAt`。
4. `active=false`（logout/密码重置/账号停用/会话不存在/所有者不匹配）：**只关闭同一 Hub 会话的所有 socket**，`close(4401, 'Session revoked')`；其他会话不受影响；正常 close handler 释放 briefcase/lease/Editor。
5. 429/5xx/网络超时/401/403/404（端点或服务凭据不可用）：视为 transient，**不关闭连接**；不得因 Hub 抖动或 MS 服务密钥轮换误断全部编辑器。
6. 合法 refresh 轮换：Hub 会话仍存在 → 连接保持。
7. 断开/关闭 socket 时清理定时器；无未 unref 的定时器阻止进程退出。
8. 日志不出现 access/refresh token；只可出现本地 sessionId、Hub sessionId 与计数。
9. B1.2c：BFF/MS 正 token 缓存默认 0；新 WS 升级/HTTP RPC/BFF `/api` 每请求回源；显式 >0 才缓存且负结果永不缓存。既有 WS socket 不宣称“下一请求”（X-20）。

### 1.4 非目标

- 不做客户端 WS 重连、ticket、WS 内 token 刷新协议。
- 不做 Hub → MS 主动推送撤销；依赖周期探测。
- 正 token 缓存默认关闭（B1.2c）；既有 WS socket 的周期撤销延迟登记 X-20，不宣称“下一请求”。
- 不做 per-iModel ACL、OBO、真实归因、jti denylist、session TTL。
- 不改 Part Studio/Feature RPC/账本/checkpoint/version/storage。
- 不勾选 G1 Gate。

## 2. Hub 内部 session-status 探针

### 2.1 契约

```text
GET /internal/auth/sessions/:sessionId/status?userId=<userId>
Headers (service-only):
  X-Service-Token: <Hub service JWT>   # G1 B6 P2 首选；scope session.status
  # 或显式 legacy（off / AUTH_SERVICE_LEGACY_API_KEY=allow）：
  # X-API-Key: <AGENT_API_KEY>        # MS 的 IMODELHUB_API_KEY 同值
  # X-Service-Name: modeling-server
→ 200 { "active": true | false }
```

- 路由文件：`imodelhub-services/src/session/session-status.controller.ts`；`SessionModule` 注册。
- 鉴权：**2026-11-24 B6 P2 起**为 `ServiceAuthGuard` 双模：优先签名 service token（scope `session.status`，服务名=`AUTH_OBO_SERVICE_NAME`，`X-Service-Token` 或 Bearer）；legacy `X-API-Key` + pinned `X-Service-Name` 仅在服务客户端 off 或显式 `AUTH_SERVICE_LEGACY_API_KEY=allow` 时接受。不是用户 JWT 路径，用户 JWT 被拒绝。MS 侧 provider/transport 与 canary 见 `AIRR-2026-11-23-B6-SERVICE-IDENTITY-P0.md` §5.2/§5.3。
- `active=true` 当且仅当：session 行存在（未软删）、session owner 与 `userId` 一致、账号 `status=active` 且未软删。
- 缺失/无效 id/owner 不匹配/inactive/deleted 全部折叠为 `{ active: false }`；不返回 PII、不返回 token、不区分失败原因。
- 该端点不能读取用户数据，只能回答会话存活；持有 MS 服务密钥者已具备服务级数据面权限，新增信息面仅为布尔值。

### 2.2 为什么不是 `/auth/me`

`/auth/me` 校验 access token；refresh 轮换后旧 token 必然 401。MS 若用旧 token 复验会在每次 refresh 后误判撤销。session-status 探针与轮换解耦，且不把 token 保留在 MS 连接记录中。

### 3.1 失败语义

| Hub 探针结果 | MS 行为 |
|---|---|
| 200 `{active:true}` | 保持；更新 `lastAuthValidatedAt` |
| 200 `{active:false}` | 关闭同一 `hubSessionId` 的所有 socket（4401）；其他会话不动 |
| 401/403（服务凭据错误） | 保持；按 unavailable 处理（避免密钥轮换误断所有人） |
| 404（Hub 未部署该端点） | 保持；按 unavailable 处理（部署顺序容错） |
| 429/5xx/超时/网络错误 | 保持；transient |
| 检查异常 | 保持；transient |

### 3.2 性能/负载

- 每个 WS socket 每 30s 一次内部 HTTP 探针；带 `hubSessionId` 的 socket 才注册。
- Hub 侧为 session 主键查询（user eager），复用现有 session 行；无新表/迁移。
- 每 socket 一个 `setInterval`，已 `unref()`；当前规模可接受，未来连接数大时可改为单一调度器/批量探针。
- Hub 全局限流在连接数很高时可能对探针返回 429；MS 按 transient 保活（不断连），代价是撤销感知延后。规模阶段应为该内部端点配置独立宽松桶或批量探针。
- **B1.2c 已修**：BFF/MS 正 token 缓存默认 `AUTH_TOKEN_CACHE_TTL_MS=0`，新 WS 升级/HTTP RPC/BFF `/api` 每次回源，撤销下一请求生效；仅显式 >0 时缓存，且只缓存成功结果。既有 WS socket 仍是周期复验，最大健康延迟约 30s + 探针 ≤5s，登记 X-20。

## 7. B1.2c 补强：正 token 缓存默认关闭（2026-11-23）

### 7.1 问题

B1.2a 让 Hub 在下一请求拒绝旧 token，但 BFF `createTokenValidator` 与 MS
`validateTokenWithPrincipal` 仍缓存 60s 正结果（MS 还缓存负结果）。在这 60s
内，已 logout/撤销的 token 仍可被 BFF `/api` 或新的 MS WS/HTTP RPC 请求接受，
削弱“下一请求 401”的结论。既有 WS socket 也只在 60s 定时器上复验。

### 7.2 变更

- BFF 与 MS 新增 `AUTH_TOKEN_CACHE_TTL_MS`，**默认 0（禁用正缓存）**；每次
  BFF `/api`、MS WS 升级、MS HTTP RPC 认证都回源 Hub。显式 >0 是性能选项，
  会重新打开 ≤TTL 的撤销窗口，文档明确标注，不作为默认/不宣称安全。
- 缓存只存成功结果；**负结果（401/revoked）与 'unavailable' 永不缓存**。
- BFF 旧 env `AUTH_CACHE_TTL_MS` 不再读取（防止 compose 旧默认 60s 静默重新
  打开窗口）；`docker-compose.yml` 的 BFF 服务改用
  `AUTH_TOKEN_CACHE_TTL_MS: ${BFF_AUTH_TOKEN_CACHE_TTL_MS:-0}`。
- 既有 WS socket 的复验间隔默认从 60s 降至 **30s**；仍未实现每消息复验，登记
  `EXCEPTIONS.md` **X-20**：Hub 可达时最大撤销延迟约 30s + 探针 ≤5s；Hub
  不可达时延长到恢复后的下一次探针；新连接/HTTP/BFF 不受此窗口影响。

### 7.4 真实性与残余

- 既有 WS socket 不是“下一请求 401”：X-20 已登记 owner/失效日期/退出计划；
  不在文档或报告中宣称即时。
- 显式 `AUTH_TOKEN_CACHE_TTL_MS>0` 会重新引入窗口；仅性能部署可选，默认不启用。
- 本补强不改 Hub 行为；B1.2a 的隔离 relational Hub e2e（18/18 + 7/7）仍有效。
- MS WebSocket 真栈仍未验证：需要部署新 Hub+MS 后执行 logout→≤30s 内 4401
  关闭、refresh 保持、429/5xx 不误断的 socket 实测。
