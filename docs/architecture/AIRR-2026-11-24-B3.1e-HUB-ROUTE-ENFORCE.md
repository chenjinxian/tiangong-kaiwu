## 0. 结论摘要

1. **只强制已有元数据的内容路由**：`AUTHZ_ENFORCE=read` 时，带
   `@RequirePermission` 的读路由（GET/HEAD）不再接受仅凭 `X-API-Key` 的旁路；
   `write` 覆盖同一批路由的所有方法。未带元数据的 46 条 B3.1a 例外**保持
   legacy**，在本文与 X-27 中显式列明，不得宣称 Hub 路由 PEP 完整。
2. **共享 key 不是授权通道**：enforce 下，有效 `X-API-Key` + 有效用户 JWT 的
   请求会继续走既有 RBAC（`ResourceAccessGuard` 等价逻辑）；仅 key 无用户时
   fail closed（401）。`off` 完全保持现行行为。
3. **签名服务主体不回归**：`request.servicePrincipal` 仍只按路由显式
   data-plane scope 判定，绝不回落到 key/RBAC；scope 是服务级、不是单 iModel
   绑定，该边界在本文和后续 B3.1f 中保留。
4. **路由元数据门禁升级为“有元数据且挂载 ACL guard”**：B3.1a 只验证元数据存在；
   本切片增加测试断言，防止未来出现“有元数据但无 guard”的假覆盖。
5. **默认关闭、可回滚**：无迁移；`AUTHZ_ENFORCE=off` 即恢复。`full` 仍被
   启动校验拒绝（storage/link 不在本切片）。
6. **未完成**：46 条例外、iTwin favorites/recents 无 ACL 写、access-control
   子资源 IDOR、files、baseline failed/requeue、`/imodels/admin/*`、
   服务 scope 未绑定单 iModel、MS/BFF/WA/storage/tile 均不在本切片；真实
   归因/审计与 N-1 运营验证仍未闭环。

## 1. 范围与非目标

### 1.1 本切片范围

1. 将 Hub `AuthzEnforce` 从仅 `off` 扩为 `off|read|write`；`full` 与其他值启动失败。
2. 在 `SystemAgentOrResourceGuard` 中把“有效共享 key”从**授权旁路**降为
   **仅传输因子**：
   - enforce 命中内容路由（有 `@RequirePermission` 元数据且方法在范围内）时，
     不再 return true；
   - 若请求带有效用户 JWT，则继续走既有 RBAC 分支；
   - 若无用户主体，401 fail closed；
   - 无 `@RequirePermission` 元数据的服务/系统路由行为不变。
3. `read` 只覆盖 GET/HEAD；`write` 覆盖全部方法（含读）。按 HTTP 方法分类，
   不做请求体语义推断。
4. 保持 `@RequireServiceAuth(profile=data-plane)` + 签名 service token 的
   scope-only 分支不变。
5. 路由元数据门禁测试增加“每个带 `@RequirePermission`/`@RequireServiceAuth`
   的 handler 必须在 handler 或 class 上挂载对应 ACL guard”的断言；
   现有 46 条例外不要求 ACL guard，但必须有登记。
6. 启动日志输出 enforce 模式、受影响的 guard、legacy 例外数量与关闭方式；
   不打印 key/token/查询串。
7. 在隔离 Hub 栈上跑 read/write canary：非成员用户 + 共享 key 在 enforce 下
   403；`off` 下旧行为保留；管理员 RBAC 允许；写路由在 `read` 下仍 legacy、
   在 `write` 下 403。

### 1.2 明确非目标

- 不给 46 条例外补元数据、不改 controller 路由、不删除 legacy 路由。
- 不修 access-control 子资源 IDOR、iTwin favorites/recents、iTwin image delete。
- 不改 files、baseline failed/requeue、`/imodels/admin/*`、storage/SAS、tile、
  BFF、MS、WA、worker。
- 不实现 `full`，不改变 service token 的 scope 模型或签发/校验。
- 不新增审计表/事件；不改变 resolver 语义；不新增用户可见行为。
- 不跑 live DB、不部署镜像、不勾 Gate；不宣称 B3/X-21/X-27 关闭。

## 2. 语义

### 2.1 模式

| `AUTHZ_ENFORCE` | 行为 |
|---|---|
| `off`（默认） | 完全保持现行：有效 `X-API-Key` 可在 `SystemAgentOrResourceGuard` 路由旁路 RBAC。 |
| `read` | 带 `@RequirePermission` 且方法为 GET/HEAD 的路由：有效共享 key 不再旁路；有用户走 RBAC，无用户 401。其他方法保持 legacy。 |
| `write` | 带 `@RequirePermission` 的所有方法：有效共享 key 不再旁路；有用户走 RBAC，无用户 401。 |
| `full` | **启动失败**（未实现；storage/link 等留给后续切片）。 |

`AUTH_SERVICE_LEGACY_API_KEY=allow` 只控制 legacy 通道是否可登记；enforce 命中
内容路由时该 allow **不能**覆盖强制。`AUTH_SERVICE_CLIENTS_ENABLED=off` 与
`shadow` 下行为一致：enforce 是更高优先级的门禁。

### 2.2 主体判定顺序

1. `request.servicePrincipal`（签名 service token）：只按路由 data-plane scope
   判定；失败 401/403。不变。
2. 有效 `X-API-Key`：
   - `off` 或路由不在 enforce 范围：维持 legacy 旁路（`isServiceRequest` 标记）；
   - enforce 范围：记录 `legacy_api_key_not_authorization`，**不设置**
     `isServiceRequest`，继续第 3 步。
3. 用户 RBAC：缺失用户 → 401 `Legacy service key is not an authorization channel`；
   有用户 → 与 `ResourceAccessGuard` 相同的元数据检查（iTwin/iModel/repository），
   403/404 语义不变。
4. 无元数据路由：维持现状（服务/系统/未分类例外）。

### 2.3 读/写分类

- `read = GET|HEAD`；`write = 全部方法`。
- 方法缺失（测试/非 HTTP 调用）不视为读；`read` 不强制，`write` 强制。
- 这是保守的分类：POST 查询类接口在 `read` 下仍 legacy，在 `write` 下强制。

| iModels core | 26 | 有权限元数据；5 条 list/favorites/recents 例外不在本切片。 |

> 本文不把“有元数据”当成“已给出 ACL 结论”。

### 3.2 明确保持 legacy（B3.1a 的 46 条例外）

- iModels 列表/favorites/recents（5）、baseline `failed|requeue`（2）、
  `/imodels/admin/*`（4）、UserPermissions/UserMemberships self-check（2）、
  iTwins（13）、exports（3）、access-control 静态权限（1）、users admin（5）、
  webhooks（5）、repositories（2）、files（4）。
- 其中部分有 handler/service/custom guard 授权，部分仅共享 key 或 JWT；
  本切片**不**把它们升级为 `covered-enforce`。B3.1f 负责 fail-closed 与清理，
  B3.1g 负责负例矩阵。
- 因此 enforce 只缩小“已标注内容路由”的共享 key 旁路，不代表 Hub 数据面
  PEP 完整；X-27 退出条件不变。

## 4. 实现

### 4.1 配置

- `src/auth/config/auth.config.ts`：`AuthzEnforce` 增加 `read`/`write`；
  `authz.enforce` 从 env 读取（默认 `off`）；`full`/未知值仍由 `@IsEnum` 拒绝。
- `src/auth/config/auth-config.type.ts`：`AuthAuthzConfig.enforce` 改为
  `'off'|'read'|'write'`，注释从“P0 only”改为 B3.1e 语义。
- `src/main.ts`：启动日志输出 `AUTHZ_ENFORCE`、legacy 例外数（46）与回滚方式；
  不输出 key/token。无迁移、无新表。

### 4.2 Guard

- 在 `SystemAgentOrResourceGuard` 中新增纯函数（便于单测）：
  `isContentEnforcementActive(mode, method)` 与
  `isLegacyKeyEnforcedOnRoute(mode, method, permissionMetadataExists)`。
- Branch 2 改为：有效 key 且未命中 enforce 时才旁路；命中 enforce 时记录
  warn（reason、method、path，不含 key）并落入 Branch 3。
- Branch 3 缺失用户时，如果该请求带有效 key 且命中 enforce，抛
  `UnauthorizedException('Legacy service key is not an authorization channel')`；
  否则保持既有 `NotFoundException('Resource not found')`。
- `ResourceAccessGuard` 不变（它本就不接受共享 key 旁路；服务主体已在入口拒绝）。
- `DataPlaneAuthGuard` / `ServiceAuthGuard` / agent controllers 不变。

### 4.3 路由门禁

- 扩展 `test/unit/authorization/pep-route-metadata.spec.ts`：
  - 对每个带 `@RequirePermission` 的 handler，断言 handler/class 的
    `GUARDS_METADATA` 包含 `ResourceAccessGuard` 或
    `SystemAgentOrResourceGuard`；
  - 对每个带 `@RequireServiceAuth` 的 handler，断言包含
    `SystemAgentOrResourceGuard` / `ServiceAuthGuard` / `DataPlaneAuthGuard`；
  - 例外目录不变；新增“元数据有 guard 缺失”反例 fixture，证明门禁会失败。
- 不新增 controller 注册表；仍覆盖 B3.1a 的 27 个内容 controller。

### 4.4 测试

- 配置：`off/read/write` 通过；`full`/`on`/空值非法；默认 `off`。
- Guard：
  - `off`：有效 key 旁路（既有断言保留）；
  - `read`：GET 内容路由 + 有效 key + 非成员用户 → RBAC 403；管理员 → allow；
  - `read`：POST 内容路由 + 有效 key → 仍旁路（显式文档化）；
  - `write`：POST 内容路由 + 有效 key + 非成员用户 → RBAC 403；
  - 无用户 + 有效 key + enforce → 401，且不设置 `isServiceRequest`；
  - 签名 service principal + 正确 scope → allow（不受 enforce 影响）；
  - 无元数据路由 + 有效 key → 保持旁路；
  - 日志不含 key/token/查询串。
- 门禁：guard 存在性正向 + 缺失反例。
- 隔离 Hub canary（`tests-b31e`）：
  - `AUTHZ_ENFORCE=off` 控制组：outsider JWT + `X-API-Key` 对已标注 GET
    内容路由返回旧行为（allow）；
  - `AUTHZ_ENFORCE=read`：同一请求 403；admin JWT + key allow；POST 写路由
    仍按 legacy（预期 allow）；
  - `AUTHZ_ENFORCE=write`：同一 POST 写路由 403；admin allow；
  - Hub 日志无 key/token/查询串；用后 `down -v`、删临时文件。
  - 不证明 MS 全链路；不碰 live DB。

## 6. 风险、残余与待决

1. **部分强制**：46 条例外仍未受路由 ACL 保护；enforce 不覆盖它们。不得宣称
   B3.1e 完成 Hub 数据面 PEP，亦不得关闭 X-27。
2. **共享 key 仍可触达系统/例外路由**：baseline/admin、files、部分 handler
   自校验路由仍接受 key；B3.1f/X-21 处理。
3. **服务 scope 未绑定单 iModel**：签名 service token 仍是服务级信任，拥有
   scope 即可对该类路由的任意 iModel 操作；服务侧审计/资源绑定留给后续。
4. **IDOR 未修**：access-control 子资源与 iTwin image delete 的跨 iTwin
   绑定问题不在本切片。
5. **favorites/recents 未修**：iTwin 级 6 条写路由仍无 ACL，列表按 userId
   过滤；B3.1f 处理。
6. **read 模式下 POST 读接口仍 legacy**：按方法分类的保守取舍；写校验必须
   等 `write`。
7. **默认 off**：不改变现网行为；enforce 需运营显式开启，缺少部署形态
   canary/回滚演练。
8. **未做真实归因/审计**：本切片不新增审计事件，服务/用户主体变更仍依赖
   既有日志；B7/X-21 未闭环。
9. **不勾 Gate**：G0 ARB 未签字，G1 Gate 仍未勾选；B3 未完成。
