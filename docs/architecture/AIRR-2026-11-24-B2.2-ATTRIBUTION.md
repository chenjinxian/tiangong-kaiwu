## 0. 结论摘要

1. **当前归因有三条互不一致的路径**：
   - changeset：普通 JWT 用 `req.user.id` 写 `creatorId`；签名 service principal 写 `creatorId=NULL`、`creatorName=service:<name>`；legacy 共享 key + 人类 admin 服务账号走服务账号 JWT，changeset 仍归到 admin 用户。
   - briefcase：`create` 在 legacy service 通道接受 body `userId`，否则回退 `req.user.id`；`acquire`/`release` 直接用 `req.user.id`。官方 `ownerId` 是非空字符串，当前没有服务 actor 的官方表示。
   - OpLog：仅当运行在已建立的连接会话内时，`payload.author` 由 `SessionContext` 派生；无会话的 IPC/HTTP/CLI 路径不写 author。客户端传入的 `sessionId`/`user` 不能作为作者。
2. **当前 Hub audit 只有授权决策**：`audit_events` 只由 `AuthzDecisionsService` 写入 `eventType='authz.decision'`，没有 changeset/briefcase/NV/extended-data 写审计；表结构没有 `hubSessionId`/`clientInstanceId`/`requestId`/`resourceId`。B7 v1 的哈希规范已冻结，不能原地扩字段。
3. **推荐 actor 模型**：显式区分 `user`、`service`、`user_via_service`（OBO）、`legacy_service_account`、`unknown`；服务 actor 永不映射为人类；OBO 必须以“用户委托”身份同时满足动作与 iModel 绑定；所有身份只从已校验凭据派生，绝不取 body/header 自报。
4. **推荐 push 路径**：不替换官方客户端的全局 `Authorization`，也不做 ALS fork；由 MS 的官方 `restClient` 装饰器在精确的 Hub changeset 写路由上额外发送 `X-OBO-Token`，同时保留 `X-Service-Token`。Hub 同时校验二者：service token 证明“哪个服务”，OBO 证明“哪个用户、被允许做什么、哪个 iModel”。这是 OBO 的一种传输形态，不是第二套信任根，也满足官方 SDK 的公开扩展点约束。
5. **推荐审计**：新增独立的 `write_audit_events`（新哈希链 `write-audit.v1`）与业务写入同事务，而不是修改已冻结的 `audit_events` v1。changeset/briefcase/NV 的官方字段仍保持官方 DTO；新增归因列只作为内部事实，不新增公共 DTO。
6. **分阶段**：`legacy`（默认）→ `shadow`（派生并记录，不改官方字段）→ `enforce`（官方 creator/owner 改为真实用户；`user_required` 路由拒绝无 OBO 的 service-only 写；显式 `service_allowed` 系统路由才保留 null/service；审计同事务）。任何阶段都可回退到 legacy，不需要重写历史行。
7. **主要阻塞**：`ADR-G0-16` 未 ARB 签字；OBO 尚未被 Hub 数据面 guard 接受；B6 共享 key/人类 admin 未退役；B4 Write 未激活（显式 Edit 用户仍不能写）；官方 SDK 无 per-request 用户 Authorization；briefcase 官方 `ownerId` 对 service-owned 无语义；B10 `tenantId` 缺失；handle 15m 上限与 WS ticket 未完成；B7 v1 链规范冻结。

## 1. 目标、验收与非目标

### 1.1 目标

1. 让 Hub 的 changeset、briefcase、named version、extended-data 写入能够回答“真实用户是谁、代表哪个服务、哪个会话/请求”。
2. 让纯后台服务写入明确标记为 service actor，不伪造人类用户；让 legacy 人类 admin 服务账号写入明确标记为 legacy，而不是混入真实用户。
3. 把 OpLog 作者固定为服务端派生的连接 principal，并在 payload 中保留可审计的会话/请求关联。
4. 为上述写入提供与业务提交同事务的审计事实；失败时不得产生“有写入、无归因”的行。
5. 不改变官方 changeset/briefcase/NV REST DTO 的既有语义；内部新增字段只服务审计与查询。
6. 给出可回滚的分阶段开关，历史行不回填、不改写。

### 1.2 可观察验收（Proposed，未执行）

### 2.7 官方 SDK 约束（读只读产物）

- `IModelsClientOptions.headers` 是同步 `HeaderFactories`，无请求上下文，不能按 URL 或会话 await 刷新。
- `IModelsClientOptions.restClient` 是官方公开 `RestClient` 接口，可按请求装饰；P4a 已用该接缝按 P3 路由注入 `X-Service-Token`。
- 官方 changeset create 请求体不接收 `creatorId/creatorName`；服务端必须派生。
- 官方 briefcase acquire 载荷没有 owner 字段；owner 只能从服务端认证身份派生。
- 官方 `Briefcase.ownerId` 是非空字符串；没有服务 actor 类型。

这些约束决定了：不能靠“把 userId 放进官方请求体”实现归因；不能在没有额外 header/guard 的情况下把 OBO 只放在 `Authorization`；也不能在官方 DTO 里无契约地塞 service owner。

## 3. Proposed 统一 actor 模型

### 3.1 ActorRef

> 状态：Proposed。所有字段为内部审计事实；不新增公共 DTO。

```text
ActorRef {
  actorType: "user" | "service" | "user_via_service" | "legacy_service_account" | "unknown"
  actorUserId: string | null          // 真实用户；service/legacy 时为 null
  actorService: string | null         // "service:<name>"；user 时为 null
  onBehalfOfUserId: string | null     // OBO 的用户 sub；user_via_service 时等于 actorUserId
  authSessionId: string | null        // Hub session id
  clientInstanceId: string | null     // 连接/标签实例
  attributionSource: "obo_token" | "user_jwt" | "service_token" | "legacy_shared_key" | "none"
  attributionVersion: 1
  requestId: string                   // 服务生成/校验的关联 id
  operationId: string | null          // MS 单次操作/事务 id
}
```

### 3.2 派生规则（必须全部满足）

| # | 规则 |
|---|---|
| R1 | 身份只从已校验凭据派生；body 的 `userId`、header 的 `X-Service-Name`、客户端 `sessionId/user` 都不是权威身份。 |
| R2 | OBO 优先级最高：OBO 的 `sub` 是 `actorUserId`，`actService` 是 `actorService`，`sid` 是 `authSessionId`；同时要求 OBO 的 `iModelId` 与路径一致、请求动作在 OBO scope 内、session 仍 active。 |
| R3 | 普通用户 JWT：`actorType=user`，`actorUserId=sub`，`authSessionId=sessionId`，`actorService=null`。 |
| R4 | 签名 service token：`actorType=service`，`actorUserId=null`，`actorService=service:<name>`；绝不写 `request.user`。 |
| R5 | 共享 `X-API-Key` + 人类 admin JWT：`actorType=legacy_service_account`，`actorUserId=null`，`actorService=service:<configured-name>`；不得当成真实用户。 |
| R6 | 无凭据/无会话：`actorType=unknown`；仅允许 legacy 行；enforce 写入口拒绝。 |
| R7 | OBO 不得由服务账号换取；OBO 的 `sub` 不得在服务账号 denylist 内；OBO 不得跨 iModel/跨动作复用。 |
| R8 | service-only 写入不得声称 `onBehalfOfUserId`；如未来要代表用户，必须走 OBO 或另立签名 actor claim，不得用 body。 |
| R9 | 每个写入行只允许一个 ActorRef；同一行不得同时“用户 + 未知”。冲突时 fail closed。 |
| R10 | 审计的 `requestId` 只用于关联，不作为授权；日志不得包含 token/handle/OBO 明文。 |

### 3.3 资源字段映射（Proposed）

| 资源 | 官方字段（不变） | 新增内部字段（Proposed） | 说明 |
|---|---|---|---|
| changeset | `creatorId`、`creatorName` | `actor_type`、`actor_service`、`on_behalf_of_user_id`、`auth_session_id`、`request_id`、`attribution_source`、`attribution_version` | `user_via_service` 时 `creatorId=sub`、`creatorName=NULL`；`service` 时 `creatorId=NULL`、`creatorName=service:<name>`；legacy 时按现状 |
| briefcase | `userId`（ownerId） | `owner_type`、`owner_service`、`on_behalf_of_user_id`、`auth_session_id`、`request_id`、`attribution_source`、`attribution_version` | 本切片只支持 user/OBO owner；service-owned 见 §9 决策点 |
| named version | `createdBy` | `actor_type`、`actor_service`、`on_behalf_of_user_id`、`auth_session_id`、`request_id`、`attribution_source`、`attribution_version` | 用户/OBO 才可创建 |
| changeset extended data | `createdBy` | 同上 | 用户/OBO 才可创建 |
| locks | 无 owner 列 | 不新增 owner 列；`releasedBy` 保持；写审计以 briefcase owner + actor 记录 | 锁是 briefcase 的派生状态 |
| OpLog | `payload.author`（JSON） | `author.actorType`、`author.hubSessionId`、`author.clientInstanceId`、`author.opId`、`author.requestId` | 无 EC schema 迁移；payload JSON 追加 |

**公开 DTO 规则**：changeset 官方 `creatorId` 仍可为 null；briefcase 官方 `ownerId` 仍非空；named version/extended data 官方 `createdBy` 仍为字符串。新增内部列不进入官方响应。若未来要让客户端看到“service actor”，必须另立 DTO/ADR，不得现在偷偷改变 `creatorId` 语义。

## 4. Push 路径：OBO vs signed actor claim

### 4.1 选项比较

| 方案 | 做法 | 优点 | 缺点/风险 | 结论 |
|---|---|---|---|---|
| A. OBO 作为全局 `Authorization` | 替换 `ServiceAccountAuthClient` 为 ALS 感知的 `AuthorizationClient`，push 时返回当前会话 OBO | 最接近标准 HTTP 语义；Hub 数据面 guard 只需接受 OBO | 官方 SDK 全局调用 `getAccessToken`，LS/ALS 必须覆盖 `BriefcaseDb.pushChanges` 全链路；并发会话易串 token；native/异步边界未证实；回退复杂 | 不作为首切片 |
| **B. OBO 作为额外签名 actor header** | 保留服务账号/服务 token 的 `Authorization`+`X-Service-Token`；在精确 Hub changeset 写路由额外发送 `X-OBO-Token` | 不 fork/patch SDK；不依赖 ALS；按请求绑定 iModel/动作；Hub 可同时校验 service 与 user；可回退 | 新增内部 header 契约；guard 需双凭据校验；OBO 仍是 bearer（但已有短 TTL/单 iModel/可撤销） | **推荐（Proposed）** |
| C. 新建专用 signed actor claim | 为归因单独设计 JWT/HMAC claims | 可只做归因 | 第二套信任根、第二套撤销/过期/审计；与 OBO 重复；易被误用为授权 | 拒绝 |
| D. 继续用人类 admin 服务账号 | 不改 | 零改动 | changeset/briefcase 仍归 admin；违反 B2.2 | 拒绝 |

### 4.2 推荐流程（Proposed）

```text
MS pushChanges（已通过 B3.1d 的 doc.write + changeset.push 决策）
  → 官方 IModelsClient changesets POST/file/complete
  → dataPlaneRestClient 分类器命中 Hub changeset 写路由
  → 从连接会话取该 iModel 的 OBO（scope 必须含 doc.write + changeset.push）
  → 发送：Authorization: <service JWT 或服务模式既有头>
           X-Service-Token: <service token>
           X-OBO-Token: <single-iModel OBO>
  → Hub DataPlaneAuthGuard / OboActorGuard：
       1) 校验 X-Service-Token（签名、service、scope data.changesets.write）
       2) 校验 OBO（typ/ver/aud/exp/revoked/session/actService == service）
       3) OBO.iModelId == 路径 iModelId
       4) OBO.scope ⊇ {doc.write, changeset.push}
       5) 当前 resolver 对 OBO.sub 的精确动作仍 allow（防 5m 缓存外撤权）
       6) 设置 request.actor = user_via_service，request.user = OBO.sub（仅数据面 OBO 路径）
  → changesets.controller：creatorId = actor.actorUserId，creatorName = null
  → changesets.service：同一事务写 changeset + write_audit_events
```

说明：

- **service token 仍是授权/传输因子**，OBO 是用户归因与用户动作证明；两者必须同时存在。
- **归因策略元数据（Proposed）**：每个写路由声明 `attributionPolicy: user_required | service_allowed`。
  - `changeset.create/file/complete`、`briefcase.create/acquire/release`、锁写、NV/extended-data 写为 `user_required`；enforce 下没有有效 OBO 一律拒绝，**不允许仅凭 `data.changesets.write`/`data.briefcases.write` 降级为 service actor**。
  - 若未来出现真正的系统 changeset 写者（当前不存在），必须使用独立 closed scope（例如 `data.changesets.system_write`）并 pin 到该系统客户端；MS 用户路径不得申请该 scope。该 scope 不在本切片实现。
  - 这样“service actor”仍是合法 actor 类型，但不能成为用户路径静默回落的后门。
- **OBO 不得跨路由复用**：classifier 只对 changeset POST/file/complete 附加；briefcase acquire/release 用 `briefcase.write`；NV 用 `doc.write`；extended data/groups 用 `doc.write`。不允许把读 OBO 复用为写。
- **跨 origin 不发送**：沿用 P4a 的 Hub origin 校验；OBO 绝不发往 Azure/SAS/tile 等外部 URL。
- **OBO 失效**：401/403，不回落 service-only、不回落共享 key、不静默降级为 legacy admin。MS 在发送前若拿不到 OBO，enforce 返回 `AuthorizationUnavailable` 503（不产生 changeset）；shadow 记录 `attribution_missing` 并继续 legacy。
- **官方 SDK 约束**：`X-OBO-Token` 通过 `RestClient` 装饰器加入；不改 `headers` 同步工厂、不改官方 client、不手写 changeset REST。

### 4.3 失败语义

| 场景 | Hub | MS shadow | MS enforce |
|---|---|---|---|
| 无 service token / 错 service / 缺 scope | 401/403 | 记录 `service_identity_*`，继续 legacy | 503/403，不 push |
| 有 service token、无 OBO | `user_required` 路由 403 `attribution_required`；`service_allowed` 路由才允许 service actor | 记录 `attribution_missing`，继续 legacy | 预检失败 503，不 push；若已发送则按 Hub 403 透传，不重试 |
| OBO 过期/撤销/session 撤销 | 401 | 记录 `obo_*`，继续 legacy | 503，不 push |
| OBO 的 iModel 不匹配 | 403 `imodel_mismatch` | 记录，继续 legacy | 403，不 push |
| OBO scope 不含动作 | 403 `insufficient_scope` | 记录，继续 legacy | 403，不 push |
| 当前 resolver 已撤权（OBO 未过期） | 403 `insufficient_permission` | 记录，继续 legacy | 403，不 push |
| 审计插入失败 | 事务回滚 | 记录审计失败，不改变 legacy | 503，无 changeset |
| OBO 版本未知 | 401 | 记录，继续 legacy | 503 |

**硬规则**：任何失败都不得回落服务账号人类归因、不得把 service actor 写成用户、不得产生“有 changeset 无 actor”的行。

## 6. 同事务归因

### 6.1 Hub 写入

| 写入 | 当前事务 | Proposed |
|---|---|---|
| changeset create | 已有 `runInTransaction` + advisory lock + insert | 在同一 `manager` 事务内写 changeset 行（含 actor 列）+ `write_audit_events` 行；任一失败回滚；不额外开连接 |
| briefcase create/acquire | `insertBriefcase` 已有 `runInTransaction` + advisory lock | 同上；actor 列 + 审计同事务 |
| named version create | 当前是“查 changeset + 查重 + repository.create”，未见统一事务 | 建议包成一个事务（advisory lock 按 `(iModelId, name)`），行 + 审计同事务 |
| extended data create | 当前 repository.create | 建议包成事务，行 + 审计同事务 |
| lock write | 已有 locks service 事务/owner 校验 | 本切片不新增 lock 审计；若加，同一事务追加；不改变锁语义 |

**事务边界硬规则**：

1. 审计插入必须在业务 insert/update 的同一 DB 事务内，不能 afterCommit/outbox 才写。
2. 审计失败时 enforce 必须回滚业务行；shadow 可以记录失败但不改变 legacy 结果（由 `WRITE_AUDIT_MODE` 控制）。
3. 不接受“先写 changeset，后异步补审计”；这会产生不可归因窗口。
4. 不接受“审计写入成功但业务回滚”的孤儿行；同一事务保证一致。
5. **锁顺序固定**：业务资源锁（如 changeset 的 advisory lock、briefcase 的取号锁）先获取，再获取 `write_audit_events` 链锁；禁止反向获取。所有写路径遵循同一顺序，避免资源锁与审计链锁互相等待。
6. 审计链锁是全局串行点；首切片接受写路径串行化，但必须在 canary 记录 p95/队列；高吞吐前需评估分片/批量，不得静默放宽一致性。

### 6.2 OpLog

- OpLog 与 op 在同一 `EditTxn` 内写入；`payload.author` 由 `SessionContext` 派生，**已经满足“同事务”**。
- Proposed 追加 `hubSessionId/clientInstanceId/opId/requestId/actorType` 到同一个 payload；不引入第二套 local log。
- **跨系统限制**：Hub 审计与 iModel OpLog 不可能同一事务。B2.2 只要求 Hub changeset 级归因同事务；per-op Hub 审计列为非目标。push 后 changeset 的 `creatorId` 绑定该用户，OpLog 仍留在 briefcase 内。
- 无会话（HTTP/CLI/单测）路径继续保持“无 author，legacy 行”；enforce 撤销只允许本会话 author，已由现有 `OPLOG_AUTHOR_FILTER` 实现。

### 6.3 请求/操作关联

- MS 为每次 push/acquire/NV 生成 `requestId`/`operationId`（服务端生成，不是客户端可伪造的身份），通过 `X-Request-Id`/审计列传递。
- Hub 只把它当关联 id；若缺失可生成；不因缺失拒绝（除非未来合规要求）。
- `authSessionId`/`clientInstanceId` 只来自已校验 OBO/JWT/handle，不来自 body。

## 7. 分阶段、开关与回滚（Proposed）

### 7.1 开关

| 服务 | 开关 | 默认 | 允许值 | 语义 |
|---|---|---|---|---|
| Hub | `ATTRIBUTION_MODE` | `legacy` | `legacy`/`shadow`/`enforce` | legacy 不读 OBO header；shadow 派生 actor/审计但不改官方 creator；enforce 改官方字段并要求 OBO（用户触发写） |

非法组合：Hub `ATTRIBUTION_MODE=enforce` 且 `OBO_DATA_PLANE_MODE!=enforce` 启动失败；MS enforce 且无 OBO 能力启动失败；enforce 且 `WRITE_AUDIT_MODE!=enforce` 启动告警（建议硬失败，由 owner 决定）。

### 7.2 阶段

| 阶段 | 行为 | 晋级条件 | 回滚 |
|---|---|---|---|
| 0. Schema only | 迁移加列/表；代码不写 | 迁移 up/down；旧 fixture 可读 | down（空表） |
| 1. Shadow | MS 发 OBO header；Hub 派生 actor 并写审计（可选）；官方 creator/owner 不变 | 单测/契约/relational e2e；真栈双用户 shadow；审计可查；无 token 日志 | 关 MS/Hub shadow；列保留 |
| 2. Enforce attribution | 用户触发写 `creatorId=sub`/`ownerId=sub`；`user_required` 路由的 service-only 写拒绝；若未来存在显式 `service_allowed` 系统写，才允许 null/service；审计同事务 | 阶段 1 证据；回退演练；B3.1d gate 打开；handle 续期可接受 | `ATTRIBUTION_MODE=legacy`；历史行不变 |

### 7.3 回滚

- 首选开关回退：Hub/MS `ATTRIBUTION_MODE=legacy`、`OBO_DATA_PLANE_MODE=off`、`WRITE_AUDIT_MODE=off`；不删列、不改历史行。
- 已写审计保留（append-only）；不自动删除。
- 迁移 down 仅在 `write_audit_events` 空或已导出/归档后执行；与 B7 相同 fail-closed 规则。
- 不可“只删 actor 列但保留代码写入”；必须先回退代码。
- 回滚后新写入恢复 legacy 归因；旧行不修复。

## 8. 测试与证据计划（Proposed，未执行）

> 本节是计划，不是结果。不得把计划写成已通过。

### 8.1 Hub 单元/契约

1. ActorRef 派生：user JWT、service token、OBO、legacy key+admin、无凭据；优先级与冲突 fail closed。
2. OBO：错 iModel、错 service、错 scope、过期、撤销、session 撤销、service account、未知版本 → 401/403。
3. changeset：user → creatorId=sub；service → null + `service:<name>`；legacy → 现状；OBO → user_via_service。
4. briefcase：普通 JWT 指定他人 403；OBO 不能指定他人；service-only create/acquire 按决策拒绝或标记。
5. NV/extended data：用户/OBO 正确 createdBy；service-only 拒绝。
6. 审计：同事务；审计失败回滚；append-only 触发器；查询过滤/分页；无 token。
7. 迁移：up/down；旧行 NULL；无改写；索引存在。
8. 日志：Logger spy 扫描 token/handle/OBO/secret。

### 8.2 Hub relational e2e（真实 Postgres）

夹具：两个用户 A/B、一个 admin 服务账号、两个 iTwin、secured/unsecured iModel、一个 changeset/briefcase/NV。

用例：

1. A 用 OBO push：changeset creator=A；actor 列 user_via_service；审计同事务；B 看不到 A 的 token。
2. service-only push：在 shadow/legacy 或显式 `service_allowed` 系统路由下 creator=null，creatorName=service:modeling-server；无人类 link；`user_required` + enforce 下必须 403。
3. legacy admin push：按 `ATTRIBUTION_MODE` 标记 legacy；不伪装 A。
4. A acquire briefcase：owner=A；B acquire 自己的；A 不能 release B 的。
5. NV/extended data：A 创建；service-only 403。

### 11.2 精确 header / 路由矩阵

MS 仅在 URL 属于配置的 Hub origin 时分类；相对 URL 按官方 client 的 Hub base URL
解析。任何其他 origin（storage/SAS/响应里的绝对链接）**不附加** OBO。活跃模式下
调用方传入的 `X-OBO-Token` 不被信任：先删除，有会话 OBO 且该请求已附加签名
`X-Service-Token` 时才写入。

**MS 客户端实际覆盖（本切片）**：

| 官方 RestClient 请求 | operation | 需要的已授予 scope | 前置 |
|---|---|---|---|
| `POST /imodels/:iModelId/changesets` | `changeset.create` | `doc.write` + `changeset.push` | 已附加 `X-Service-Token` |
| `POST /imodels/:iModelId/changesets/:id/file` | `changeset.file` | `doc.write` + `changeset.push` | 同上 |
| `POST`/`PATCH /imodels/:iModelId/changesets/:id/complete` | `changeset.complete` | `doc.write` + `changeset.push` | 同上 |

明确**不附加**：所有 GET/读路由；`changesets/.../extendeddata`；changeset
`locks/release`；locks 写；**全部 briefcase 写（create/acquire/update/release）**；
**全部 named-version 写（create/update/delete）**；named version checkpoint PUT；
baselinefile；thumbnail；非 Hub origin。briefcase/NV 是 legacy 数据面路由，
Hub 不接受没有签名服务身份的 OBO；其归因阻塞于 B6 P4b，本切片不宣称。

JWT 与 `X-API-Key` 完全不变。

### 11.3 行为语义

| 场景（MS） | `off` | `shadow` | `enforce` |
|---|---|---|---|
| 写路由分类 | 不分类、不查 OBO | 分类并解析会话 OBO | 同 shadow |
| 无签名 `X-Service-Token` | — | **不解析、不附加**（Hub 会拒绝无服务身份的 OBO） | 同 shadow |
| 有签名服务身份且会话有覆盖 OBO | — | 附加 header | 附加 header |
| 无会话/无 OBO/解析失败 | 无影响 | 记录 `attribution_missing`（或 sanitized code）、**原请求不带 header 继续** | 在调用 inner transport 前抛 `AuthorizationDenied`（403，`attribution required (...)`）；零请求、无 mutation |
| Hub 对带 OBO 请求返回 401/403 | — | 记录 `rejected`+`legacy_retry`，丢弃该 OBO，**同一请求重试一次且不带 `X-OBO-Token`** | 记录 `rejected`，丢弃该 OBO，**不重试、不降级**，错误原样上抛 |
| 身份来源 | — | 只从 `SessionContext` 的连接会话及其 OBO 缓存/句柄派生 | 同 shadow |
| body `userId`、`X-Service-Name`、入站 header | — | 一律不作为身份；不回落共享 key/服务名 | 同 shadow |

OBO 解析规则：同一 `iModelId`、未过期、`grantedScopes` 覆盖该路由全部 action；
缓存中只有 `doc.read` 的 token 永远不会用于写路由。若缓存无覆盖 token 且能从该
会话已登记的 briefcase 记录取得服务端派生的 `iTwinId`，复用现有 handle 做一次
scope 精确 exchange；否则记录 `itwin_unavailable`。不新增第二套 token/信任根。

**Hub 行为**：`off` 不读 header、不在请求上挂 `writeAttribution`、不写新列/审计；
`shadow` 尽力解析 OBO（无签名服务身份时 OBO 无效），解析成功记录
`user_via_service`，失败记录 `legacy_service_account`/`service`/`unknown`，但绝不
拒绝、绝不改官方 `creatorId`/`ownerId`/`createdBy`；`enforce` 对服务中介写要求
有效 OBO（绑定路径 iModel 且覆盖路由 action），失败在 handler 前 401/403/503，
成功时仅对已实现字段用 OBO 用户替换官方 creator/owner/createdBy。审计写入在
`shadow` 用 savepoint 隔离失败（不改变业务结果），在 `enforce` 失败则业务事务
回滚。`write_audit_events` 是应用级 `write-audit.v1` 哈希链，**不是 WORM**，也
没有 DB trigger/离站副本/链头锚定；仅有插入 API。

### 11.6 残余与启用阻塞（诚实记录）

1. **Hub `enforce` 当前不可与 MS 一起启用**：MS 只能为 changeset 写提供 OBO；
